# Pipeline

gitview turns git history and GitHub API data into five JSON files in `public/data/`. The frontend reads only those files — nothing is recalculated from git in the browser. This page maps the whole flow and explains each arrow.

## The full flow

```text
git log --all --no-merges --numstat        GitHub GraphQL API            git tag + GitHub REST API
  (per repo, pool of 4)                     (token: .env / gh)            (notes + tag dates)
        │                                        │                              │
        ▼                                        ▼                              ▼
data/gitview.db                            public/data/github.json       public/data/releases.json
(node:sqlite, incremental)                 (PRs + reviews)               (tags + release notes)
        │
        │  aggregate (buckets in GITVIEW_TIMEZONE)
        ├──────────────────────────────► public/data/stats.json   (dashboard aggregates)
        └──────────────────────────────► public/data/commits.json (last 100 commits/author)

team.local.json + stats.json + github.json
        │
        └──────────────────────────────► public/data/team.json    (devs + teams + candidates)

public/data/*.json ──► check-data.ts ──► gate: shape + invariants (error = collection fails)
public/data/*.json ──► static frontend (Vue 3 + Vite + ECharts) — reads only public/data/
```

`data/gitview.db` and `public/data/*.json` are gitignored artifacts — always regenerated by the collectors, never committed.

## What each arrow does

### git log → data/gitview.db

`collect.ts` runs `git log --all --no-merges --numstat` in each repo (streaming), normalizes every commit — UTC ISO date, canonical author name via aliases — and inserts it into SQLite (`node:sqlite`, table `commits`, primary key `(repo, hash)`). The insert is `INSERT OR IGNORE`, so re-running the collection never duplicates rows.

:::info Why don't merges count?
Merge commits carry `+0−0` diffs but inflate commits/day, pace and streaks — 17.6% of the scanned history was `Merge …` commits. The "production" of a merge already shows up in the PR. So `collect.ts` removes them in the `git log` call by topology (`--no-merges`), not by subject: a single-parent commit whose subject says "Merge" (squash or rewritten pull) still counts. Old history already in the database keeps its merges — run `pnpm clean && pnpm collect` to apply the rule retroactively. See [issue #7](https://github.com/Enlighten-Brasil/gitview/issues/7).
:::

### data/gitview.db → stats.json + commits.json

`collect.ts` aggregates the table into time buckets (week, month, heatmap, commit types) and per-author/per-repo rollups, writing `stats.json`; `commits.json` gets the last 100 commits per author, newest first. The aggregation runs in `GITVIEW_TIMEZONE` — more on that in [Collectors](./collectors.md).

### GitHub GraphQL API → github.json

`collect-github.ts` fetches all OPEN PRs plus MERGED PRs from the last 400 days, with reviews inline (1 request per page of 100 PRs), and maps GitHub logins to canonical dev names. Auth comes from `GITVIEW_GITHUB_TOKEN` (`.env` or shell) with `gh auth token` as an optional bridge.

### git tag + GitHub REST API → releases.json

`collect-releases.ts` reads local tags (`git tag`) for universal coverage and enriches them with name, notes and URL from the GitHub REST API. Commit counts per release come from `data/gitview.db` and compare timestamps, never strings.

### team.local.json + stats/github → team.json

`collect-team.ts` merges your `team.local.json` (dev profiles, teams, bots) with identities seen in the collected data, producing `team.json` — devs, teams and unmapped candidates. It runs last because it reads the `stats.json` and `github.json` generated before it.

### check-data.ts: the gate

`check-data.ts` reads the five JSONs and checks structure plus cross-file invariants (e.g. the per-author, per-repo and monthly sums must all equal `totals.commits`). Any error exits with code 1 — the collection fails and you fix the data before trusting the dashboard. Quality warnings print but never block.

## What "incremental" means

Re-running the collection is cheap by design:

- **Git side**: each repo gets `--since=<watermark>` on the `git log` call, where the watermark is the newest commit date already in the database for that repo minus a 7-day margin (it covers commits with old committer dates merged after the watermark). The `INSERT OR IGNORE` makes the overlap harmless. `--full` ignores the watermark and rescans everything; `--reaggregate` skips git entirely and only re-applies aliases and re-exports the JSONs.
- **GitHub side**: `collect-github.ts` refetches only PRs updated since the last collection (1-day margin) and merges them into the previous `github.json`. Merged PRs are preserved; the fresh OPEN list is the truth. `--full` ignores the cache for the fetch (but keeps the previous file as a safety net for repos that fail).

## Where the UI fits

The frontend is 100% static: `pnpm build` produces a `dist` that only fetches the JSONs in `public/data/`. The interactive parts live in the dev server only:

- The setup wizard (`/setup/*`) and the settings screens (`/settings`) use Vite plugins with `apply: 'serve'` — in the static build those routes and their endpoints do not exist.
- The `/__*` endpoints (`/__collect`, `/__setup/*`, `/__auth/*`, `/__team/*`, `/__clean`) are dev-only. The collection button ↻ in the navbar is rendered only in dev.

So a production deploy is: run the collectors wherever you want fresher data, publish `dist` + `public/data/`. No server, no database, no token on the host that serves the dashboard.
