# Pipeline

gitview produces eight fixed JSONs in `public/data/`. The frontend reads only the artifacts it needs; nothing from git is recalculated in the browser. `data/gitview.db` and `public/data/*` are gitignored, always regenerated by the collectors.

```text
git log --all --no-merges --numstat        GitHub GraphQL API            git tag + GitHub REST API
  (per repo, pool of 4)                     (token: .env / gh)            (notes + tag dates)
        │                                        │                              │
        ▼                                        ▼                              ▼
data/gitview.db                            public/data/github.json       public/data/releases.json
(node:sqlite, incremental)                 (PRs + reviews)               (tags + release notes)
        │
        │  aggregates (buckets in GITVIEW_TIMEZONE)
        ├──────────────────────────────► public/data/stats.json   (dashboard aggregates)
        ├──────────────────────────────► public/data/daily.json   (day-precise aggregate)
        ├──────────────────────────────► public/data/commits.json (last 100 commits/author)
        └──────────────────────────────► public/data/report-commits.json (complete classified history)

git for-each-ref + git log/rev-list --no-merges
  (per repo, pool of 4, async spawns)
        │
        └──────────────────────────────► public/data/branches.json (branch inventory + status)

team.local.json + stats.json + github.json
        │
        └──────────────────────────────► public/data/team.json    (devs + teams + candidates)

public/data/*.json ──► check-data.ts ──► gate: shape + invariants (error = collection fails)
public/data/*.json ──► 100% static frontend (Vue 3 + Vite + ECharts): reads only public/data/
```

## What each arrow does

### git log → data/gitview.db

`collect.ts` runs `git log --all --no-renames --no-merges --numstat` in each repo, normalizes the commits (canonical author via aliases, UTC ISO date) and inserts into SQLite (`data/gitview.db`, key `(repo, hash)`, `INSERT OR IGNORE`). It is incremental by default: it collects from a watermark onward with `--since`. Merge commits stay out of all metrics; modes and rule in [Collectors](./collectors.md).

### data/gitview.db → stats.json + daily.json + commits.json + report-commits.json

In one SQLite pass, `collect.ts` aggregates `stats.json` and `daily.json`, exports the legacy `commits.json` sample (7-hex hashes, last 100 commits of each author, newest first) and writes `report-commits.json` with the complete classified history. The report uses full 40-hex hashes and the same canonical `day` as `daily.json`, after the same date/scope skips; rows are ordered by timestamp descending, then repo and hash ascending. It is a lazy artifact for the next reports phase, with no UI loader yet. The buckets and day keys come from `GITVIEW_TIMEZONE`, never from the machine's timezone, and report emission adds no git scan.

### GitHub GraphQL API → github.json

`collect-github.ts` fetches all OPEN PRs and the MERGED PRs of the last 400 days, with reviews inline in the same query (cursor pagination beyond 100). Auth via `GITVIEW_GITHUB_TOKEN` (`.env` or shell), with `gh auth token` as an optional bridge.

### git refs → branches.json

`collect-branches.ts` enumerates `refs/heads` of each clone (tip + committer date) and computes, per branch, ahead/behind vs the production ref and vs the first integration ref — merges out of every count — plus the raw e-mails (`%ae`) and +/− lines of the authors ahead of production. Each branch gets exactly one status of a closed union (`production`, `integration`, `feature`, `bot`, `pousada`); links to PRs are computed by the frontend joining `github.json` (`headRef`). It runs only in the full chain — the light re-collection skips it (no fetch, the result would be identical).

### git tag + GitHub REST API → releases.json

`collect-releases.ts` reads local tags (`git tag`) for universal coverage and enriches them with name, notes and URL from the REST API. The commit count between tags comes from `data/gitview.db` and compares timestamps, never text.

### team.local.json + stats/github → team.json

`collect-team.ts` merges `team.local.json` (profiles, teams, bots) with the identities seen in the data: devs, teams and unmapped candidates. It runs last because it reads `stats.json` and `github.json`.

## check-data.ts: the gate

Reads the eight fixed JSONs and checks structure and cross-file invariants, including bidirectional `report-commits.json` reconciliation with every daily group and the stats totals/maps. An error takes the collection down with exit 1; warnings never block. The per-file list is in [Data model](./data-model.md).

## What is dev-only

The `dist` from `pnpm build` fetches only the JSONs in `public/data/`; the wizard (`/setup/*`), *Configurações* (Settings, `/settings`) and the `/__*` endpoints (`/__collect`, `/__setup/*`, `/__auth/*`, `/__team/*`, `/__clean`) exist only in the dev server.

Production deploy: run the collectors where the data needs to be fresh and publish `dist` + `public/data/`. No server, no database, no token on the machine serving the dashboard.
