# Data model

The frontend consumes exactly five JSON files from `public/data/`. They are gitignored artifacts regenerated by the collectors, but their shape is a contract: `check-data.ts` fails the collection when a field the UI reads disappears. This page documents each file — keys first, then what the gate requires.

## Summary

| file | holds | written by |
|---|---|---|
| `stats.json` | aggregates: weekly/monthly/heatmap/monthlyTypes/perAuthor/perRepo/repoUrls/totals | `collect.ts` |
| `commits.json` | last 100 commits per author | `collect.ts` |
| `github.json` | PRs (OPEN + MERGED 400d) with reviews, login→dev map | `collect-github.ts` |
| `releases.json` | tags, commits per tag, unreleased count, release notes | `collect-releases.ts` |
| `team.json` | devs, teams, unmapped candidates | `collect-team.ts` |

Rules that apply to all five: top-level object with `generatedAt` (ISO timestamp of the run), author names already canonical (aliases applied at collection time), commit dates in UTC ISO with milliseconds. Lists are sparse — zero rows are simply absent (no `commits: 0` filler).

## stats.json

### Keys

| key | shape | meaning |
|---|---|---|
| `generatedAt` | ISO string | when the file was generated |
| `repos` | `string[]` | repo names included in the collection |
| `repoUrls` | `{ [repo]: string }` | web URL per repo (GitHub remotes only) |
| `authors` | `[{ name, emails, bot }]` | canonical authors and every e-mail seen for each |
| `totals` | `{ commits, additions, deletions, activeDays, repos, authors }` | global rollup |
| `perRepo` | `[{ repo, commits, additions, deletions, authors, lastCommit }]` | per repo, sorted by commits desc |
| `perAuthor` | `[{ author, commits, additions, deletions, repos, activeDays, lastCommit, streak, longestStreak }]` | per dev, sorted by commits desc; `streak` counts consecutive active days ending at the last active day |
| `weekly` | `[{ week, repo, author, commits, weekend, night }]` | ISO week key `YYYY-Www`; `weekend`/`night` are subsets (night = 22:00–05:59 in the canonical timezone) |
| `monthly` | `[{ month, repo, author, commits, additions, deletions }]` | month key `YYYY-MM` |
| `heatmap` | `[{ author, repo, month, weekday, hour, commits }]` | `weekday` 0–6, `hour` 0–23; last 24 months only |
| `monthlyTypes` | `[{ month, repo, author, type, commits }]` | conventional-commit type (`feat`, `fix`, …) or `outros` |

```json
{
  "author": "Ana Silva",
  "commits": 11523,
  "additions": 3494030,
  "deletions": 2964009,
  "repos": 14,
  "activeDays": 1312,
  "lastCommit": "2026-10-09T20:21:58.000Z",
  "streak": 5,
  "longestStreak": 53
}
```

### What check-data requires

- `generatedAt` valid ISO; `repos` a list of strings; `repoUrls` an object.
- First item of `authors`/`perRepo`/`perAuthor`/`weekly`/`monthly`/`heatmap`/`monthlyTypes` carries the expected fields (see table); `authors[].bot` is boolean.
- **The core invariant**: Σ`perAuthor.commits` = Σ`perRepo.commits` = Σ`monthly.commits` = `totals.commits`.
- `totals.additions`/`deletions` ≥ 0; per-author counts ≥ 0; `heatmap.weekday` in 0–6 and `hour` in 0–23; `monthly.month` matches `YYYY-MM`.
- `perRepo[].lastCommit` parses as a date (warning if it is in the future — author clock wrong, breaks the incremental watermark).

## commits.json

### Keys

| key | shape | meaning |
|---|---|---|
| `generatedAt` | ISO string | when the file was generated |
| `commits` | `[{ hash, repo, author, date, message, additions, deletions }]` | last 100 commits per author, newest first |

`hash` is the abbreviated 7-hex form; `message` is the commit subject (capped at 500 chars in the database); `date` is UTC ISO with milliseconds.

```json
{
  "hash": "80afade",
  "repo": "<repo>",
  "author": "Ana Silva",
  "date": "2026-10-09T20:21:58.000Z",
  "message": "chore: version 1.0.7",
  "additions": 8,
  "deletions": 6
}
```

### What check-data requires

- `generatedAt` valid ISO; every item has `hash`, `repo`, `author`, `date`, `message`.
- Dates uniformly UTC (ending in `Z`) and parseable — mixed offsets would break ordering.
- Strict descending order by real timestamp (the dev profile page assumes it).
- `hash` matches `^[0-9a-f]{7}$`.
- Warning (non-blocking): merge-subject commits with zero diff in the first 4000 items — single-parent squash/rewritten pulls that inflate counts (issue #7).

## github.json

### Keys

| key | shape | meaning |
|---|---|---|
| `generatedAt` | ISO string | when the file was generated |
| `users` | `{ [login]: { name, bot } }` | every login seen (authors + reviewers) mapped to the canonical dev name |
| `prs` | `[{ repo, number, title, url, state, draft, author, createdAt, mergedAt, additions, deletions, changedFiles, reviews }]` | all OPEN PRs + MERGED PRs within the window |

PR fields: `state` is `OPEN` or `MERGED`; `mergedAt` is `null` for open PRs; `author` is the GitHub login mapped through `users` (a deleted account becomes `ghost`); `draft` marks draft PRs. `reviews` is `[{ author, state, submittedAt }]` with `state` in `APPROVED | CHANGES_REQUESTED | COMMENTED | DISMISSED | PENDING` (closed union, issue #42).

```json
{
  "repo": "<repo>",
  "number": 5,
  "title": "feat: new export",
  "url": "https://github.com/<org>/<repo>/pull/5",
  "state": "MERGED",
  "draft": false,
  "author": "ana-dev",
  "createdAt": "2026-01-23T21:06:43Z",
  "mergedAt": "2026-02-01T12:00:00Z",
  "additions": 140,
  "deletions": 32,
  "changedFiles": 3,
  "reviews": [
    { "author": "bruno-dev", "state": "APPROVED", "submittedAt": "2026-01-24T10:00:00Z" }
  ]
}
```

### What check-data requires

- `generatedAt` valid ISO; `users` is an object of `{ name: string, bot: boolean }`; first PR has `repo`, `number`, `state`, `author`.
- `state` ∈ {`OPEN`, `MERGED`}; `MERGED` carries a valid `mergedAt`.
- No `repo#number` duplicates; review `state` inside the closed union.
- No `MERGED` PR older than the 400-day window.

:::info Why only 400 days of merged PRs?
The 12-month dashboard view is the widest PR window, and 400 days covers it with slack ([issue #5](https://github.com/Enlighten-Brasil/gitview/issues/5)). Keeping every merged PR forever would grow the JSON without feeding any panel; older merged PRs expire naturally in the incremental merge. The `mergedAt` cutoff is what counts — an old PR with recent activity (rebase, comment) does not sneak back in through the `updatedAt`-based incremental fetch.
:::

## releases.json

### Keys

| key | shape | meaning |
|---|---|---|
| `generatedAt` | ISO string | when the file was generated |
| `repos` | `[{ repo, url, unreleased, tags }]` | one entry per repo |

Tag entries are newest first:

| key | shape | meaning |
|---|---|---|
| `tag` | string | tag name |
| `date` | ISO string | tag creation date (UTC) |
| `commits` | number | commits between the previous tag and this one (first tag: since the beginning) |
| `name` | string \| null | release title from GitHub (`null` without a GitHub release) |
| `notes` | string \| null | release body, truncated at 3000 chars |
| `prerelease` | boolean | prerelease flag from GitHub |
| `url` | string \| null | release URL on GitHub |

`unreleased` counts commits after the newest tag. Commit counts compare timestamps, never strings.

### What check-data requires

- `generatedAt` valid ISO; first repo entry has `repo`, `url`, `tags`, `unreleased`.
- Tag dates parseable and in descending order; `commits` ≥ 0 per tag; `unreleased` finite and ≥ 0.
- **Coverage invariant**: `unreleased` + Σ `tags[].commits` = the repo's commits in `stats.json.perRepo`.

## team.json

### Keys

| key | shape | meaning |
|---|---|---|
| `generatedAt` | ISO string | when the file was generated |
| `devs` | `[{ name, title, description, emails, githubLogins, teams, bot }]` | canonical devs (profiles + identities seen in the data); `title`/`description` come from the dev profile, `null` otherwise |
| `teams` | `[{ name, description, color, members, renamedFrom? }]` | teams from `team.local.json`; `renamedFrom` lists old names when a team was renamed |
| `candidates` | `[{ kind, id, emails?, prs? }]` | unmapped identities: `kind: "author"` (raw git name, with `emails`) or `kind: "login"` (GitHub login, with `prs` count) |

`emails` and `githubLogins` are the effective aliases used to unify identities; logins keep the API's casing (deduplicated case-insensitively). `ghost` (deleted PR author) and bots never appear as candidates.

### What check-data requires

- `generatedAt` valid ISO; first items of `devs`/`teams`/`candidates` carry `name`/`name`/`kind`+`id` respectively (plus `bot`, `emails`, `githubLogins`, `teams` on devs; `members` on teams).
- Dev names unique; every team member is a known dev.
- `candidates[].kind` ∈ {`author`, `login`}; never `ghost` (invariant M1) and never a bot login.
- No case-duplicate logins within a dev.
- Warnings (non-blocking): a team member who is also a candidate; a human dev with no aliases at all.
